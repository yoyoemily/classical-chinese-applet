## 工作约定

### 1. "继续项目"及板块触发词的行为

触发词规则如下（与 CLAUDE.md 一致）：

| 用户说 | 读取哪些文件 |
|--------|-------------|
| **继续项目** | `.claude/memory/MEMORY.md`（CLAUDE.md 始终在上下文） |
| **继续学习板块** | `.claude/memory/study/study-section.md`（无需读其他记忆，CLAUDE.md 始终在上下文） |
| **继续选篇板块** | `.claude/memory/articles/articles-section.md`（无需读其他记忆，CLAUDE.md 始终在上下文） |
| **继续经典板块** | `.claude/memory/classics/classics-section.md`（无需读其他记忆，CLAUDE.md 始终在上下文） |
| **继续我的板块** | `.claude/memory/mine/mine-section.md`（无需读其他记忆，CLAUDE.md 始终在上下文） |
| **继续修复问题** | `.claude/memory/fix/fix-guide.md`（无需读其他记忆，CLAUDE.md 始终在上下文） |

以上触发词严格匹配，不确认、不追问，直接读取对应文件即可回答问题。**除非用户明确说"结合 git"**，否则不查 git log/diff。

**收到触发词后的行为清单（逐条自检，缺一不可）**：

1. ✅ 只读对应记忆文件（1 个），不读其他任何文件
2. ✅ 读完后根据记忆文件内容，用 3-5 句话简述板块当前状态（覆盖哪些页面/功能、哪些已完成、哪些待定）
3. ✅ 简述后立刻提问："你要从哪里继续？"——**停在这里，不等回复不往下**
4. ❌ 不跑 `git log`、`git diff`、`git status` 等任何 git 命令（除非用户说"结合 git"）
5. ❌ 不自己决定"先看看 xxx 文件"——板块记忆文件已包含全部信息，相信它就是最新状态
6. ❌ 不读板块记忆以外的任何源码、不 `ls` 目录、不扫描工程

**禁止操作**：
- 不要 `ls` 扫描整个项目目录
- 不要批量读取所有页面/组件文件
- 板块文件已经记录了该板块的全部信息，足够回答问题
- 不要主动读 git log、git diff、git status（除非用户明确要求结合 git）
- **不要执行 `git add`、`git commit`、`git push` 等 git 写操作。用户自己操作 git 提交。**

### 1.1 【硬性规则】板块记忆是唯一权威——禁止补充读取源码

**收到板块触发词后，板块记忆文件是唯一允许读取的文件（CLAUDE.md 始终在上下文，无需重读）。** 记忆文件已包含该板块的全部信息：页面列表、功能状态、完成度、关键代码路径。读完记忆文件后直接进入提问环节，不做任何源码确认。

**Why:** 记忆文件就是为替代源码读取而维护的。读完记忆再读源码，等于否定记忆的权威性，浪费 token，破坏工作上下文的缓存。这条规则与第 5、6 条行为清单呼应——第 5 条说"不自己决定先看看 xxx 文件"，本条说"记忆文件之外没有需要看的东西"。

**How to apply:**
- 收到"继续 xxx 板块"后，只读对应的板块记忆文件（1 个），不读任何 `pages/` 下的源码
- 读完记忆文件 → 简述状态 → 提问"从哪里继续" → 停住等回复
- 用户指定具体任务后，再根据任务需要读取相关源码——此时才允许读
- 如果记忆文件内容不够支撑任务判断，那是记忆需要更新，不是该去读源码的理由

### 2. "更新记忆"时的行为

**更新时机**：每次任务完成后**自动**按本准则更新记忆，不等用户提醒；用户说"更新记忆"时，同样按本准则执行。

**用户说"更新记忆"不等于必须更新**：按下面准则检查后，如果没有值得更新的内容，就不更新，并明确告知"无记忆需要更新"。

有值得更新的内容时，更新 `CLAUDE.md` 和 `.claude/memory/` 中的内容。

**记录原则：只记录结果，不记录过程**

**应该记录的**（对后续开发有帮助）：
- 新增的功能模块、页面、组件
- 新增的类型、接口、常量
- 重要的架构决策和约定
- 项目完成度的变化（哪些做完了、哪些待开发）

**不应该记录的**（过程信息，无长期价值）：
- 今天做了什么、什么时候做的
- 某个功能的实现细节、中间怎么折腾的过程
- 临时的调试信息、修复过程
- "我就是这样改的"之类的叙事

### 3. 收到图片后的行为

当用户发图片让 Claude 理解时，**禁止直接理解完图片就动手修改代码**。正确的流程是：

1. 先解读图片内容，将理解结果以文字形式反馈给用户
2. 等待用户确认理解无误
3. 确认后再动手实现

**Why:** 图片理解可能不准确，直接改代码容易跑偏，浪费时间和 token。先对齐理解，再动手。

**How to apply:**
- 看到图片 → 输出"我理解图片内容是：..." → 等用户确认 → 再改代码
- 即使图片内容看起来很明显，也要先确认

### 4. 动手前的确认原则

**始终保持一个原则：动手前一定要确认过。** 这个原则适用于所有涉及代码修改、文件操作、结构调整的场景，不只是图片理解。

**Why:** 避免返工，确保方向正确。一次错误的修改比一次多余的确认成本高得多。

**改动计划模板**

每次动手改代码之前，输出一个简短的改动计划，明确 3 点：

1. **改哪个页面/文件** —— 具体到路径，如 `pages/study/index`
2. **改哪些点** —— 逐条列出，每条一句话说清楚要做什么
3. **用什么方案** —— 每条对应一个技术方案（如"在 `init()` 中调用 `wx.setNavigationBarTitle`"）

不需要长篇大论，但必须具体。不要只说"优化样式"，要说"虚线边框 + 暖色背景 + 大号图标"。

**流程**：先输出计划 → 等用户确认（"可以"、"好的"等）→ 再动手写代码。除非修改极其简单（修 typo、改一个字面量），否则不要跳过。

**How to apply:**
- 涉及多文件修改时，先输出改动计划，等确认后再动手
- 涉及结构调整时，先确认方案
- 不确定时主动询问，不要猜测用户意图
- 单文件单处修改（如修一个变量名）可跳过，直接改

### 5. 排查问题时

如果排查问题需要扫描工程各处（如 `find`、`grep`、遍历多个目录），**必须先明确询问用户确认**，而不是默认就开始大规模扫描。

**Why:** 避免不必要的 token 消耗，保护工作上下文的缓存。CLAUDE.md + 记忆文件已经覆盖了项目 90% 的信息，大多数问题可以通过这些信息直接回答。

**How to apply:** 
- 遇到需要扫描的情况，先问："这个问题需要搜索 X、Y、Z 几个地方，我可以扫描吗？"
- 如果是单文件读取，直接操作即可，不必询问

### 6. 任务完成时明确反馈

每个任务或阶段完成后，必须明确告知用户"已完成"，不要让用户猜测是否还在进行中。完成后必须输出简短汇报，列明改动文件和需要用户手动操作的步骤。

**Why:** 用户无法判断沉默是"还在干活"还是"干完了没说"。明确的完成信号让协作顺畅，不浪费用户时间等待。

**How to apply:**
- 每阶段完成后主动汇报，格式：已完成的改动 + 需要用户手动操作的
- 不要悄无声息地结束任务

### 7. 任务完成后必须汇报

每个任务完成后，必须输出简短的汇报总结，格式为：

```
已完成的改动：
- <文件/模块>：<改动内容>
- <文件/模块>：<改动内容>

需要你手动操作的：
- <操作步骤>（如果没有则写"无"）
```

**Why:** 用户需要确认改动范围并知道下一步要做什么。不汇报就是没完成。

**How to apply:**
- 每次改完代码后立即输出汇报
- 汇报要具体到文件和改动点
- 用户说"好了？"时，如果已经汇报过就说"已汇报完毕"，如果没汇报就补一个

### 8. 前端薄层原则

**核心主张**：减少视图层面的逻辑包装，让前端尽量薄。逻辑下沉到后端，前端只负责渲染。

- 后端返回的数据应"拿来即用"，前端不做 map/filter/reduce/groupBy 等二次加工
- 汇总、统计、排序、分页等逻辑由后端接口处理
- 前端只做条件渲染（`wx:if`）、样式切换、用户交互
- 前端逻辑包装前要三思（尤其是具有一定复杂度或性能损耗的），可主动提议交给后端处理

**反例**：前端拿到列表后遍历计算汇总、groupBy 分组、根据多字段组合判断生成新字段
**正例**：后端 DTO 直接返回 `summary`、`stats`、`isXxx` 等计算好的字段

### 9. 【硬性规则】JSON 文件中的中文引号

**凡写入 JSON 文件，必须严防 ASCII 双引号 `"` 出现在字符串值内部**。

中文语境下经常需要的引号用法（如引用原文、引用说法），**必须使用 Unicode 中文引号 `“` `”`（即 `“` 和 `”`）**，绝对不能使用 ASCII `"`。

**反例**（这会导致 JSON 解析失败）：
```json
{ "explanation": "孙子以"兵"指代整个军事活动" }
```

**正例**：
```json
{ "explanation": "孙子以“兵”指代整个军事活动" }
```

**Why:** JSON 规范中 `"` 是字符串定界符，值内部出现未转义的 `"` 会破坏 JSON 结构。中文引号 `“”` 是独立的 Unicode 字符，与 JSON 语法完全不冲突。

**How to apply:**
- 写 JSON 之前，先在脑中过一遍：这个文件的每个字符串值里有没有需要引用原文的地方——如果有，全部用 `“”`
- 写完 JSON 后，读回文件内容，grep 检查是否有多余的 ASCII `"` 出现在不该出现的位置
- 如果 JSON 文件较大（>10KB），**写入前先用 Python `json.loads()` 验证**，发现解析错误立即修正再写

### 10. 【硬性规则】JSON文件修改先备份

**凡是修改超过 30KB 的JSON文件，必须先复制副本**。

```bash
cp <target_file> <target_file>.bak
```

任务完成后确认文件正确，再删除备份：

```bash
rm <target_file>.bak
```

**Why:** JSON文件修改容易因多次编辑逐步损坏内容，一旦中间某步改坏，原内容就永久丢失。有备份就可以随时恢复重来。

**How to apply:**
- 修改前 `cp file file.bak`
- 每步编辑后验证（JSON 用 `python3 -c "import json; json.load(open('file'))"` 快速校验）
- 全部完成后确认无误，`rm file.bak`
- `*.bak` 应在 `.gitignore` 中（已有配置）

### 11. 【硬性规则】永远不要直接修改数据库

修复流程的铁律：**知识库 JSON 是唯一权威数据源，数据库是 JSON 导入后的镜像。** 修复时必须改知识库 JSON，由用户执行导入 API 来同步数据库。

**Why:** 数据库是 JSON 的"编译产物"。直接改数据库会与 JSON 源文件产生差异，下次导入时会覆盖掉手动修改。正确的数据管线是：知识库 JSON → 导入 API → 数据库 → 小程序读取。

**How to apply:** 任何涉及 quizItem/kidRef/definition/sentence/distractor 的修复，一律改 JSON 源文件：
1. 词书 JSON：`~/knowledge_library/文言文/词书/wb_*.json`
2. 选篇 JSON：`~/knowledge_library/文言文/选篇/正文/articles_*.json`
3. 标准义项表：`~/knowledge_library/文言文/词书/definition_standard.json`

改完后校验 JSON 语法，然后告知用户执行导入（顺序：先 articles 全量，再词书）。

### 12. 【硬性规则】禁止自动调用导入 API

**修改知识库 JSON 后，禁止自动调用后端的导入 API（如 `POST /api/admin/import` 等）。** 导入操作必须由用户在微信开发者工具中手动完成。

**Why:** 导入操作会写入数据库，涉及生产数据变更，必须由用户亲自确认和执行。AI 自动导入跳过了用户的审核环节，一旦 JSON 有误，数据库会直接污染。

**How to apply:**
- 修改完知识库 JSON 后，只做语法校验（如 `python3 -m json.tool`）
- 告知用户："数据已修改完毕，请手动调用导入 API 同步到数据库（顺序：先 articles 全量，再词书）"
- 不要在告知用户之前或之后自己执行 `curl` 调用导入接口

### 13. 【硬性规则】给方案前必须确认对话结束并征求同意

**给任何方案、计划、总结、对策之前，必须先确认用户的想法已经全部表达完（对话结束），并且征求用户同意后才给方案。讨论中途禁止抢先输出方案、对策、总结或"下一步建议"。**

**Why:** 用户在讨论阶段往往还有多个想法未表达完，过早给方案会打断用户的表达节奏、逼用户被动改口，导致方案反复推翻返工。需求讨论中用户曾连续两次纠正"别总是着急蛮荒的""我们还有很多没交流完的细节，你就咔咔一顿输出"。

**How to apply:**
- 讨论进行中，用户每表达一个想法，只做两件事：**复述确认理解** + **就未明确处提问**；不给方案、不总结、不给建议、不列计划
- 只有出现以下信号才进入方案环节：用户说"我说完了""没了""就这些"等结束信号，或用户主动说"出方案""整理计划"等
- 出方案前先复述要点清单让用户过目确认"有没有记漏、记错"，确认后才展开完整方案
- 用户说"别着急""停下来""等我""你听我说"时，立即停止输出，安静等用户继续

### 14. 【硬性规则】DDL 变更写入 schema.sql，由用户执行

**新任务涉及 DDL 变更（建表/改表/索引等）时：DDL 必须写入文言雀后端 `/Users/zhutx/IdeaProjects/classical-chinese/data/schema.sql`，并在汇报中明确通知用户去数据库手动执行。禁止自动执行 DDL、禁止只写在代码里不落 schema.sql。**

**Why:** schema.sql 是数据库结构的唯一权威源文件，与"知识库 JSON 是唯一权威数据源"同模式——数据库是文件导入后的镜像，DDL 落文件后由用户亲自执行，避免文件与库不一致。

**How to apply:**
- 涉及 DDL 的任务：先在 schema.sql 追加 DDL 段（保持与现有文件风格一致），再写对应实体/代码
- 任务完成汇报中列明"需要你手动操作的：在数据库执行 data/schema.sql 新增段（或具体 DDL 语句）"
- 不执行 `mysql` 命令行、不调用任何建表接口

### 15. 复用优先（不重复造轮子）

标准流程与现成脚本每次复用。动手前先查 `.claude/memory/` 记忆文件中的「数据维护脚本」索引（如 study-section 末尾的脚本表），确认没有现成脚本才允许新建；新建脚本必须嵌入记忆文档与脚本索引。

**Why:** 用户把触发词流程当作一键可复用的能力；新脚本意味着新维护面，重复造轮子被视作浪费与风险。

**How to apply:** 复用现成模式时要**连带数据初始值一起核对**（教训：复用分页模式时漏了 loading 初始值，守卫把首次加载直接拦掉）——不能只抄方法体。

### 16. 计划/设计文件放工程内

计划、设计稿写入工程 `.claude/plans/`，不放 `~/.claude/plans/`——放外面新会话找不到、也不随仓库归档；记忆文件中的引用一律用工程相对路径。

### 17. 内容产出控成本

批量生成词条类内容（词条/释义/例句）是数量决定的成本，不是质量思考任务，**不需要深度思考**。批量生成前先报预计规模与成本方案让用户选；默认精简 schema（先必填字段，可选字段按需补）；不自校验、不重生成（校验由主会话一次脚本完成）；控制并行数。

**Why:** 批量生成曾跑 200 万+ tokens 被用户喊停。

### 18. 规划定稿后开新会话实施

计划/规划定稿并写入项目记忆与 `.claude/plans/` 后，用户偏好**开一个新会话**实施（干净上下文更容易聚焦）。规划完成时不抢着在同一会话实施（除非用户明确要求），可提醒用户开新会话。

### 19. 流程设计精简偏好

设计任何新流程/触发词时：
- **拒绝"模式 A/B"式显式选择**：改为状态自动判定、交互零切换（如素材库有未编撰素材 → 按素材转写；无 → 训练知识转写）
- **职责单一**：独立的事用独立触发词，不在一个流程里整合另一件事
- **文档能短则短**：只留执行必需项，不固化为流程分支

**Why:** 文档内容多了聚焦困难，显式选择增加交互负担；用户多次纠正过这两点。

### 20. 流程改进常态化

执行流程中或完成后，主动观察实际踩坑点与低效点，直接改进流程记忆文件，不等待用户指出；汇报改进点时标明哪条来自实际踩坑；改进保持精简、不引入分支概念。用户常主动问"流程有需要优化的吗"。

### 21. 【硬性规则】记忆只存本项目

**本项目记忆统一存 `.claude/memory/`（并更新 MEMORY.md 索引）；禁止存到 `~/.claude/projects/*/memory/`（auto memory）等工程外位置。** 与第 16 条同模式——工程外新会话找不到、不随仓库归档。

**Why:** 曾把反馈误存到 auto memory 目录，被用户纠正“本项目的记忆都存本项目里，别存其他地方”。

**How to apply:** 一切项目记忆（流程经验、反馈、约定）写入 `.claude/memory/` 下对应文件并更新 MEMORY.md 索引；不创建任何工程外的记忆文件。

### 22. 已确认惯例直接复用，不重复探索确认

执行触发词流程前，先判断"该结论是否已在流程记忆中确认过"——已确认就直接按约定执行，**不为了保险重复探索确认**（如重读旧产物核对字段写法）。

**Why:** 执行流程时，又重读旧产物确认已固化的字段写法惯例，被用户指出“这次有结论了就直接复用经验呀”。

**How to apply:** 流程记忆文件是执行权威，字段写法等已确认惯例直接参照；不要为求稳妥重读旧产物/旧文章验证，发现流程记忆缺明确表述才补读或补写流程记忆。
